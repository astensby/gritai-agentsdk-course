02

One-time setup

~2 minutes

One install at the root, one .env file at the root, no per-folder ceremony. After this you can run any step with npm run step-N.

Before you start

Node 24 LTS (20.6+ minimum) Check with node --version. The repo pins Node 24 in .nvmrc — with nvm just run nvm use. The built-in --env-file flag every step relies on needs 20.6+.
An Anthropic API key Create one at console.anthropic.com → API Keys. The steps make real API calls, so add a little billing credit — a dollar or two covers the whole workshop.
git — and nothing else Clone the repo with git. There's no separate Claude Code install: the TypeScript SDK bundles the Claude Code binary as a dependency.

Three commands

  1. git clone <repo> && cd gritai-agentsdk-course
  2. cp .env.example .env — paste your ANTHROPIC_API_KEY
  3. npm install — installs all 14 workspaces

Then any time

  1. npm run step-1 — smallest agent loop
  2. npm run step-10 — the capstone
  3. npm run typecheck:all — sanity check

Your .env

# Required for every Claude step ANTHROPIC_API_KEY=sk-ant-... # Optional — only step 11 (Ollama) # OLLAMA_MODEL=qwen2.5-coder:14b

Why no dotenv?

Node 20.6+ has --env-file built in; this repo targets Node 24 LTS. Every step's start script reads --env-file=../.env, so the root .env is the single source of truth — no extra package, no per-step dotenv/config imports.

03

Five concepts you'll use

5 ideas

Everything the SDK adds is a variation on one of these. Once you see how they compose, the capstone reads like ordinary code.

MCP servers

A standard way to attach tools to a model. Use an external one (e.g. the filesystem server), or write your own in TypeScript as an in-process server.

step 2 · step 3

Built-in tools

Read, Write, Edit, Bash, Glob, Grep — the same toolset Claude Code uses, no MCP needed for local file work.

step 2b

Skills

Plain-Markdown files in .claude/skills/. The agent auto-discovers them and pulls one in when its description matches the task — no code change to swap behaviour.

step 4

Hooks & permissions

Intercept every tool call before it runs. PreToolUse hooks log, deny, or rewrite; canUseTool asks a human; permissionMode picks the default policy.

step 8 · step 9

Subagents

Decompose a job into specialists with their own prompt and tool whitelist. The main agent dispatches to them with the built-in Agent tool (alias Task).

0raw api
The raw Anthropic SDK

One messages.create() call. No Agent SDK, no tools — just the primitive everything else is built on.

foundation @anthropic-ai/sdk messages.create
▸
Run it
$ npm run step-0
The core call
const response = await client.messages.create({ model: "claude-sonnet-5", max_tokens: 4096, // ceiling covers thinking tokens too output_config: { effort: "low" }, // cheapest lever on cost + latency messages: [{ role: "user", content: "Explain what an AI agent is in three sentences." }], });
What you'll see

Three sentences of plain text, then Input tokens / Output tokens / Stop reason. No loop, no tool calls — just one round-trip.

Try this

Change the prompt to ask Claude to run a tool ("read this file"). It will describe running one but can't actually act — that's exactly the gap the Agent SDK closes in step 1.

1loop
Smallest possible Agent SDK program

One query() call, an async iterable of messages, no tools. The loop is the SDK; the SDK is the loop.

foundation query() async iterable
▸
Run it
$ npm run step-1
The whole program
const response = query({ prompt: "Explain what an AI agent is in three sentences.", options: { model: "claude-sonnet-5" }, }); for await (const message of response) { if (message.type === "assistant") /* text */ else if (message.type === "result") /* cost + duration */ }
Key idea

The stream emits typed messages: system (init), one or more assistant with content blocks, and a final result with cost. With no tools allowed, you'll only ever see text blocks — tool_use shows up from step 2.

2mcp ext
External MCP — the filesystem server

Plug in an external stdio MCP server (the official filesystem one) and let the agent write a haiku to a sandbox folder.

mcp mcpServers allowedTools
▸
Run it
$ npm run step-2
Key shape
mcpServers: { fs: { // the key becomes the tool prefix: mcp__fs__* command: "npx", args: ["-y", "@modelcontextprotocol/server-filesystem", sandboxDir], }, }, allowedTools: [ "mcp__fs__write_file", "mcp__fs__read_text_file", // newer name the server now prefers ],
The #1 footgun

MCP tools are denied by default. You must whitelist them. Wildcards work (mcp__fs__*); explicit names give you least-privilege.

Try this

Comment out mcp__fs__write_file. The agent will explain that it tried but the tool wasn't available — a clean reproduction of the denied path.

2bbuilt-in
Built-in tools — no MCP needed

The SDK ships Read, Write, Edit, Bash, Glob, Grep. Reach for MCP for external services; use built-ins for local files.

mcp built-in tools additionalDirectories
▸
Run it
$ npm run step-2b
The change from step 2
allowedTools: ["Read", "Write", "Bash"], // bare names, no mcp__ prefix additionalDirectories: [sandboxDir], // grants file-tool access outside cwd
Read the small print

allowedTools is an auto-approve list, not an availability whitelist. An agent with allowedTools: ["Read","Write"] can still call Bash at runtime — to actually remove a tool, use disallowedTools or the tools option. The capstone (step 10) uses both.

Try this

Edit the prompt to ask the agent to run ls via Bash first. Then add disallowedTools: ["Bash"] and rerun — it will refuse and pick a different approach.

2cstdio · http
Local & remote MCP servers

Where can a server live? On your machine, launched as a subprocess (stdio), or in the cloud, reached over HTTP. To the agent both are just mcp__<key>__<tool>.

mcp stdio type:"http"
▸
Run it
$ npm run step-2c

Ships a tiny MCP server you own (server/police-mcp.ts, ~150 lines over Norway's live police log) and points the agent at it over stdio. Pure TypeScript — no extra toolchain.

Two transports, same agent
mcpServers: { police: { // LOCAL — a subprocess (stdio) command: "npx", args: ["tsx", policeServer], // any exe that speaks MCP works }, entur: { // REMOTE — no subprocess type: "http", url: "https://…run.app/mcp", // streamable HTTP endpoint // headers: { Authorization: `Bearer ${token}` }, }, }
The stdio golden rule

A stdio server talks protocol on stdout — so all logging must go to stderr (console.error), or you corrupt the stream the SDK is reading.

The whitelist still bites

Tools are namespaced by the mcpServers key, not the server's own name, and default-deny applies to both transports: allowedTools: ["mcp__police__latest_incidents", "mcp__entur__get_departures"].

Try this

Uncomment the entur block, whitelist a couple of its tools, and ask a question that needs both servers — "Any incidents near Oslo S, and when's the next train from there?" Watch the trace pull from two prefixes.

3mcp own
A custom MCP server in TypeScript

Define your own tools with createSdkMcpServer + tool(). Canned weather data here — the next step turns this into a real API.

mcp createSdkMcpServer tool() zod
▸
Run it
$ npm run step-3
Defining a tool
// tool(name, description, inputSchema RAW SHAPE, handler) const getWeather = tool( "getWeather", "Get the current weather for a city.", { city: z.string().describe("e.g. 'Oslo'") }, // NOT z.object({...}) async ({ city }) => ({ content: [{ type: "text", text: `...` }] }) ); export const weatherServer = createSdkMcpServer({ name: "weather", version: "1.0.0", tools: [getWeather, getForecast], });
The big lever

The description string is what the model reads to decide when to call the tool. Write it well — this is the single biggest lever on tool-use quality.

Heads-up

The schema is a zod raw shape (a plain object of zod fields), not a z.object({...}). The SDK wraps it for you.

3breal api
Same tool, calling a real API

The handler now hits Open-Meteo over Node's built-in fetch. No API key, no new deps — and the agent gets actual weather.

mcp fetch open-meteo
▸
Run it
$ npm run step-3b
The payoff

The agent doesn't know or care that the tool changed. From its point of view, "getWeather" is the same tool — except now it returns real, current data.

The pattern
async ({ city }) => { const place = await geocode(city); if (!place) return friendly(`Couldn't find "${city}".`); const wx = await fetchCurrent(place); return { content: [{ type: "text", text: format(wx) }] }; }

When a fetch fails, return a friendly message — the agent reads it as a tool result and recovers gracefully.

Try this

Add a third tool — getAirQuality, also via Open-Meteo. Add it to allowedTools and watch the agent pick the right one for the question.

4skills
Skills — Markdown files that change behaviour

A skill is a folder under .claude/skills/<name>/SKILL.md. The agent reads the description and pulls the body in when the task matches.

skills settingSources .claude/skills/
▸
Run it
$ npm run step-4
The whole "code" change
options: { model: "claude-sonnet-5", settingSources: ["project"], // scope discovery to this folder }
Read the small print

The SDK default is ["user", "project", "local"] — not empty. So .claude/skills/ already loads even if you omit settingSources. Passing ["project"] scopes discovery to this folder (reproducible workshop runs); passing [] is the SDK's isolation mode and is the real way to disable skills.

Try this

Set settingSources: [] and rerun — the agent emits unstructured prose with no error. Then put it back to ["project"] and watch the skill kick in and produce the templated output.

The resume pattern
let sessionId: string | undefined; while (true) { const input = await rl.question("you > "); const response = query({ prompt: input, options: { ...baseOptions, ...(sessionId ? { resume: sessionId } : {}) }, }); for await (const m of response) { if (m.type === "system" && m.subtype === "init") sessionId = m.session_id; /* ...print text...*/ } }

7subagents
Delegate to specialist subagents

A coordinator agent dispatches to a code-reviewer and a test-planner via the built-in Agent tool (alias Task). Each subagent has its own prompt and toolset.

control agents option Agent tool
▸
Run it
$ npm run step-7
The shape
allowedTools: ["Read", "Agent", "Task"], // Agent (alias Task) is how the coordinator dispatches agents: { "code-reviewer": { description: "Reviews TS for bugs, security, code smells.", prompt: `You are a senior code reviewer. ...`, tools: ["Read", "Grep"], }, "test-planner": { /* ... */ }, }
Why decompose?

Each subagent runs in its own context window. The main agent doesn't have to hold a code review and a test plan in its head — it just dispatches and synthesises the returned bullets.

8hooks
Hooks — intercept every tool call

A PreToolUse hook for observability (log every call) and another for safety (block rm/sudo). Pure async functions in your process.

control PreToolUse permissionDecision: "deny"
▸
Run it
$ npm run step-8
The deny hook
const blockDangerousBash: HookCallback = async (input) => { const cmd = (input as PreToolUseHookInput).tool_input?.command ?? ""; if (/\brm\b/i.test(cmd) || /\bsudo\b/i.test(cmd)) { console.log(" ↑ blocked by hook"); return { hookSpecificOutput: { hookEventName: "PreToolUse", permissionDecision: "deny", permissionDecisionReason: "rm/sudo not allowed in this demo.", }, }; } return {}; // continue normally };
What you'll see

The agent writes notes.txt, then tries rm notes.txt. The hook prints ↑ blocked by hook, the deny short-circuits before the shell ever runs, and the agent gets a tool result it can recover from.

Try this

Add a rewrite hook that strips --force from any git push. Return the modified input with permissionDecision: "allow" + updatedInput.

9perms
Interactive permissions — the human in the loop

The "Claude wants to write pizza.txt — allow?" prompt, implemented in 30-ish lines of readline.

control canUseTool permissionMode
▸
Run it
$ npm run step-9
The callback
const canUseTool: CanUseTool = async (toolName, input, opts) => { if (alwaysAllow.has(toolName)) return { behavior: "allow", updatedInput: input }; const answer = (await rl.question("[y]es / [n]o / [a]lways > ")).trim().toLowerCase(); if (answer === "a") { alwaysAllow.add(toolName); return { behavior: "allow", updatedInput: input }; } if (answer === "y" || answer === "") return { behavior: "allow", updatedInput: input }; return { behavior: "deny", message: "User declined. Don't retry." }; };
Decision order
  • Is the tool in allowedTools? — auto-run
  • Do PreToolUse hooks say deny? — block (step 8)
  • Else, call canUseTool if present
  • Else default to deny
Try this

Wire the same callback into a Slack DM bot. The shape doesn't change — only the transport for the question.

10★ capstone
The capstone — a meeting-notes agent

Composes built-ins + a skill + a hook into one useful agent. Reads transcripts/*.txt, writes formatted output/*.md. Under 80 lines.

capstone Glob · Read · Write settingSources PreToolUse disallowedTools
▸
Run it
$ npm run step-10
The whole thing
const response = query({ prompt: `Process every .txt in ${transcriptsDir}: Read → use the meeting-notes-formatter skill → Write to ${outputDir}/*.md.`, options: { model: "claude-sonnet-5", allowedTools: ["Glob", "Read", "Write"], // auto-approve these disallowedTools: ["Bash"], // actually remove the shell additionalDirectories: [transcriptsDir, outputDir], settingSources: ["project"], // scope skill discovery hooks: { PreToolUse: [{ hooks: [logEveryCall] }] }, }, });
What it brings together
  • Built-in tools (step 2b) — Glob + Read + Write
  • Skills (step 4) — meeting-notes-formatter drives the output shape
  • Hooks (step 8) — PreToolUse logs every call so you can watch it work
  • Tool restriction — disallowedTools keeps it off the shell (because allowedTools doesn't)
Try this

Drop your own transcript into transcripts/ and rerun. Edit .claude/skills/meeting-notes-formatter/SKILL.md to change the output template — no code change needed.

11alt sdk
Same ideas, different SDK + local model

Vercel AI SDK v6 with a local Ollama model. The agent ideas are portable; only the glue changes.

alt streamText @ai-sdk/mcp ollama
▸
Prerequisites
  • Ollama running locally: brew install ollama && ollama serve
  • A tool-capable model: ollama pull llama3.3 (or qwen2.5-coder)
Run it
$ npm run step-11
What stays the same
  • System prompt, tools (custom + MCP), and a loop
  • The skill discovery idea — but the Vercel SDK has no skill primitive, so src/skills.ts rolls a tiny loader that mimics the convention
Honest caveats

Local models are bounded at tool use. Small models (<30B) often hallucinate tool calls or skip them. Steps 7–9 patterns mostly still work; subagents and complex skill templates struggle. Claude Agent SDK + Claude remains the production-quality default.
